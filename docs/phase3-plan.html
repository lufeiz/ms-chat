2 P3-1 · Scheduler 批处理 无新依赖

动机

流式输出时一个同步突发里有 N 次 update()，当前每次都同步 emit changed → 订阅者 N 次 re-render。把 changed 合并成每 microtask 一次。

设计 src/v2/core/Scheduler.ts

class Scheduler {
  schedule(fn: () => void): void;  // 同一 fn 一个 microtask 内只跑一次
  flush(): void;                   // 立即同步执行挂起任务
  get pending(): boolean;
}

接入 BaseListStore

  • 细粒度事件（message:add/remove/update）保持同步（携带具体 payload）。
  • changed（快照信号）改为 scheduler.schedule(emitChanged) —— 一个 microtask 内多次 mutate 只发一次。
  • 暴露 store.flush()（委派 scheduler）给需要同步的场景 / 测试。
  • getSnapshot() 始终同步返回最新（只有事件被延迟，读不延迟）。

更改步骤

  1. 新增 src/v2/core/Scheduler.ts，导出加入 v2/core/index.ts。
  2. 改 BaseListStore：持有 Scheduler，emitChanged() 走 schedule；加 flush()；destroy() 里 flush + 清空。
  3. 改 ChatStore.destroy() 调用各 store flush（避免 microtask 泄漏）。
  4. 用 queueMicrotask（降级 Promise.resolve().then）。

完整测试用例

tests/v2/Scheduler.test.ts

  1. 去重：同一 fn 一个 microtask 内多次 schedule → 只执行一次
  2. 不同 fn 都执行
  3. flush() 立即同步执行并清空队列
  4. flush 后再 schedule → 下个 microtask 再跑（队列重置）
  5. microtask 边界：await Promise.resolve() 后自动 flush
  6. 重入：schedule 内部再 schedule → 下一轮处理，不死循环
  7. pending 反映队列状态
  8. 隔离：fn 抛错不阻断同批其他 fn

追加到 tests/v2/MessageStore.test.ts

  1. 批处理：同步连续 3 次 add → changed 只 emit 1 次（microtask 后），但 message:add emit 3 次
  2. getSnapshot() 在 add 之后、microtask 之前已是最新（读不延迟）
  3. flush() 后 changed 立即可见
  4. add 后 remove 同一 tick → changed 一次，最终快照正确
  5. destroy() flush 挂起的 changed 且之后不再 emit

验证

tsc + vitest（fake timers / await flushMicrotasks）+ build DCE 0 残留 + react demo 实测：流式 30Hz 更新，用 React Profiler 对比接入前后 re-render 次数（预期 N 次/突发 → 1 次/microtask）。

3 P3-2 · ThemeManager v2 无新依赖

动机

v1 findChangedValues 只递归 1 层（com→son），三层及以上改动 静默失效（H10）；getThemeConfig 用 JSON.parse(JSON.stringify) 深克隆，主题深时慢 （P3）。

设计 src/v2/theme/ThemeManager.ts（继承 v2 EventEmitter）

type ThemeEvents = { 'theme:change': [theme: Readonly<ThemeConfig>, changes: ReadonlyArray<ThemeChange>] };
interface ThemeChange { path: string; cssVar: string; oldValue?: string; newValue?: string; }

class ThemeManager extends EventEmitter<ThemeEvents> {
  getThemeConfig(): Readonly<ThemeConfig>;        // 引用稳定, frozen, setTheme 后才换新
  setThemeConfig(updates: DeepPartial<ThemeConfig>): void;
  // 内部: 任意层级递归 diff → 扁平 CSS var path(--mschat--a--b--c)→ 批量 apply → emit
}

关键点

  • 深度递归 diff：任意嵌套层级收集变更叶子（修 H10）。
  • 结构化共享：setTheme 合并出新 frozen 树，未变子树复用引用（替代 JSON 深克隆，修 P3）；getThemeConfig 返回稳定 frozen 根。
  • CSS var 命名：扁平路径 --mschat--${keys.join('--')}，2 层与 v1 完全兼容，深层自然延伸。
  • 删除语义：新树缺失的叶子 → removeProperty。
  • SSR 守卫：typeof document !== 'undefined' 才操作 DOM；无 document 仍维护状态 + emit。

更改步骤

  1. 新增 src/v2/theme/ThemeManager.ts + src/v2/theme/index.ts，v2/index.ts 加 export * from './theme'。
  2. 实现 deepDiff（收集 ThemeChange[]）、structuralMerge（写时复制）、applyCssVars、toCssVarPath。
  3. DeepPartial<T> 类型工具放 v2/core 或就近。
  4. v1 src/theme/themeStore.ts 头部加 @deprecated，迁移指南补 ThemeManager 条目。

完整测试用例

tests/v2/ThemeManager.test.ts（jsdom）

  1. 浅层（2 层）变更 → 对应 --mschat--com--son 写入 document.documentElement.style
  2. 深层（3 层及以上）变更触发对应 CSS var（回归 H10）
  3. 未变更字段不触发 setProperty（spy 调用次数）
  4. 同次 set 多个变更 → 批量 apply，theme:change emit 一次，changes 含全部路径
  5. 值设为 undefined/null → removeProperty
  6. 引用稳定：getThemeConfig() 多次调用返回同引用，直到下次 setThemeConfig（修 P3）
  7. 返回值 frozen（dev 下改抛错）
  8. theme:change payload：(theme, changes)，change 含 path/cssVar/oldValue/newValue
  9. 结构化共享：未变子树在 set 后保持引用相等
  10. 初始 config 经构造函数 apply
  11. SSR：document 为 undefined 时不抛错，仍 emit theme:change
  12. EventEmitter 能力：on('theme:change') 返回 disposer 可取消
  13. 嵌套 + 删除混合：一次 set 同时新增/改/删，CSS var 对应 set/remove 正确

验证

tsc + vitest（jsdom，spy style.setProperty/removeProperty）+ build + react demo：加主题切换按钮，实测深层主题改动生效（对照 v1 失效）。

4 P3-3 · MarkdownWorker（Web Worker 解析） 新依赖

动机

流式每个 chunk 都 re-parse markdown（高亮/表格）在主线程抢帧（P4 主因）。迁到 Worker。

设计 src/v2/workers/

class MarkdownWorkerClient {
  constructor(opts?: { poolSize?: number; coalesce?: boolean });
  parse(req: { id: string; source: string; options?: ParseOptions }): Promise<ParseResult>;
  cancel(id: string): void;
  dispose(): void;
  isFallback(): boolean;   // 无 Worker 时主线程降级
}
  • 池（poolSize，默认 1）、coalesce（同 id 新请求自动 cancel 旧的，治流式堆积）、Transferable（大 source 用 ArrayBuffer）、SSR/降级（typeof Worker==='undefined' → 主线程同步 parse，API 不变）。
  • Worker 内用纯 markdown lib；不引 React/Vue。
  • 接入：core 提供 client，react/vue demo 负责实例化注入（不强耦合）。

更改步骤

  1. 新增 protocol.ts（消息类型）、markdown.worker.ts（Worker 实现）、MarkdownWorker.ts（主线程 client）、index.ts；v2/index.ts 导出 client。
  2. new Worker(new URL('./markdown.worker.ts', import.meta.url), { type: 'module' })（vite 原生）。
  3. vite.config 处理 worker 入口；package.json 加 marked + @vitest/web-worker（devDep）。
  4. 主线程 fallback 路径共享同一 parse 实现。

完整测试用例

tests/v2/MarkdownWorker.test.ts（@vitest/web-worker）

  1. 基础 parse：markdown → html + meta（headings/codeBlocks 数正确）
  2. 并发 3 个不同 id → 全 resolve，html 互不串
  3. coalesce：同 id 两次请求，先发的被 cancel（reject AbortError），后发 resolve
  4. 主动 cancel(id) → 对应 promise reject
  5. dispose() 后 parse 调用 reject 'disposed'
  6. SSR fallback：globalThis.Worker=undefined → isFallback() true，parse 主线程完成，行为一致
  7. worker 抛错 → 该 id reject，其他 in-flight 不受影响
  8. poolSize>1 负载均衡（spy）
  9. 空 source → 空 html，不崩
  10. options（highlightLanguages/streamingMode）透传

验证

tsc + vitest（web-worker 插件）+ build（确认 worker chunk 产出）+ react demo：流式渲染接入 worker，Performance 面板对比主线程 long task（预期 30ms+/chunk → <5ms）。

6 架构建议

先 P3-1 + P3-2。

这两个零新依赖、收益明确（批处理直接砍流式 re-render；ThemeManager 修 H10 深层失效 + 去 JSON 深克隆），风险可控。

P3-3 MarkdownWorker 牵涉新依赖 + Worker 构建 + 测试基建，且 RFC 里它本就是"可选注入"，独立成一轮更稳。若做，Markdown 库选 marked（轻、Worker 友好）。
